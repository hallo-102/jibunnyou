# 初開催日のマスタ権限エラーと監視表示の修復

2026-11-14 06:45:16、本番スケジューラの朝処理が `racedata_results.xlsx` の `PermissionError` で終了した。06:45:51に追加ループが自動再試行し、rootの復旧処理はオッズ取得へ進んでいた。

## 原因と修復

本番スケジューラはUID 1004、GID 10で動く。一方、11月13日のマスタ更新後は所有者root、結果マスタ0770、レーティングマスタ0700となっていた。`publish_pair()` が作業ファイルを `copy2()` でコピーし、作業用アクセス権まで本番へ持ち込んでいた。初回検証は主にrootの追加サービスで行われ、本番UIDによる読み取りの検証が不足していた。

更新前バックアップの0644を2ファイルに復元した。内容SHAは修復前後で不変。本番スケジューラのUID 1004でopenpyxlを実行し、結果159シート、レーティング7シートを開けることを確認した。

- 結果SHA: `6c776804a3883621015203df2c0f7b70ebaa29fc31628921db72511509ece0bf`
- レーティングSHA: `1d3dc27f0ef9dade157f042a34f2637d07c278b6c92a2f81feddfc718c1179c6`

再発防止として、置換前の本番ファイルのアクセスメタデータ・所有UID/GID・モードを一時ファイルへ継承するよう修正した。NAS上の回帰試験では、更新元0600・更新先0644/UID1004の条件で、内容更新後も0644と所有者が保たれることを検証した。既存朝処理と進行中の自動再試行は停止・重複起動していない。本番重みは変更していない。

## 監視の古い表示

Windowsの通常のUNC読み取りは06:45:16のFAILEDを返す一方、NAS上の同一パスは06:45:51のRUNNINGだった。通常読み取りでは状態更新の反映を確認できなかったため、NASの独立した観測サービスから5秒ごとに一意名のスナップショットを発行する方式を追加した。

観測サービスは既存イメージを使い、業務データを読み取り専用mountし、専用観測フォルダだけに書き込む。外部公開ポート・SSH依存・追加認証はない。Windowsで新しいファイル名の観測を読み、NASのRUNNINGおよび更新中のログが見えることを確認した。Windowsアプリも更新・再起動した。

ループの`checked_at`は長い子処理の間に進まないため、画面用NAS観測時刻と区別する。黄色の「ループ状態の更新待ち」は完了でも停止確定でもなく、最後の業務状態更新が古いことを示す。現在工程とログも併せて確認する。
